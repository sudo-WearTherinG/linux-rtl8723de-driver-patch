1. Hardware & System Overview

The Realtek RTL8723DE M.2 combo adapter integrates two distinct host bus interfaces onto a single silicon die. Both functions share internal power-management and coexistence resources, along with a single 1x1 2.4 GHz antenna.

2. The Two Distinct Issues on RTL8723DE

Issue A: Complete Loss of Wi-Fi and Bluetooth After Warm Reboot

Classification: Kernel driver shutdown / hardware reset sequencing issue.

When performing a warm reboot (reboot / systemctl reboot) from a cold boot with internal Bluetooth active, both the USB Bluetooth controller and PCIe Wi-Fi adapter fail to initialize during the subsequent boot.

Kernel Log Evidence

1. USB Bluetooth enumeration fails first:

usb 1-6: new full-speed USB device number 3 using xhci_hcd
usb 1-6: device descriptor read/64, error -71
usb 1-6: Device not responding to setup address.
usb 1-6: device not accepting address 5, error -71

Error -71 corresponds to EPROTO (USB protocol error).

2. PCIe Wi-Fi subsequently fails MAC power-on:

rtw88_8723de 0000:02:00.0: Firmware version 48.0.0, H2C version 0
rtw88_8723de 0000:02:00.0: failed to poll offset=0x5 mask=0x1 value=0x0
rtw88_8723de 0000:02:00.0: mac power on failed
rtw88_8723de 0000:02:00.0: failed to power on mac
rtw88_8723de 0000:02:00.0: failed to setup chip efuse info
rtw88_8723de 0000:02:00.0: probe with driver rtw88_8723de failed with error -16
Register-level observation

The polled register offset 0x5, with mask 0x1, corresponds to BIT_APFM_ONMAC in REG_APS_FSMCO + 1.

The observed failure indicates that the Auto Power-On MAC state machine does not reach the expected state during initialization. The probe subsequently fails with -EBUSY (-16).

The shared power-domain reset explanation is the working hardware-level hypothesis based on the observed behavior, rather than a confirmed internal silicon diagnosis.

Issue B: 2.4 GHz Single-Antenna Coexistence Throughput Collapse

Classification: Bluetooth/Wi-Fi coexistence performance limitation.

When streaming A2DP Bluetooth audio over internal Bluetooth (0bda:b009) while connected to a 2.4 GHz Wi-Fi network using rtw88_8723de, Wi-Fi throughput can degrade severely.

Observed Symptoms

  • Wi-Fi RX bitrates collapse to approximately 1–2 MBit/s.
  • CCK 1M modulation may appear during degradation.
  • Kernel logs report firmware TX-report failures.
rtw88_8723de 0000:02:00.0: failed to get tx report from firmware

Root-Cause Analysis

The RTL8723DE is a 1x1 single-antenna combo device. Bluetooth and 2.4 GHz Wi-Fi must share the available RF resources.

Time-division multiplexing (TDMA) arbitration between Bluetooth SCO/A2DP activity and Wi-Fi traffic is handled through Realtek's coexistence mechanism and firmware.

During continuous Bluetooth audio streaming, the observed behavior suggests that Wi-Fi transmission and reception opportunities become severely constrained.

Verified Workaround

Disable the internal Realtek Bluetooth controller (0bda:b009) and offload Bluetooth audio to an external USB Bluetooth adapter.

This removes the internal combo chip's Bluetooth activity from the shared RF coexistence equation and eliminates the observed single-antenna contention.

3. Empirical Reboot State Matrix

Controlled testing across cold boots and consecutive warm reboots established the trigger condition on the unpatched 7.2.15 kernel.

Initial State Before Reboot Warm Reboot #1 Warm Reboot #2
(from broken state)
Cold boot → BT ON, Wi-Fi ON FAIL PASS
Cold boot → BT ON, Wi-Fi OFF FAIL PASS
Cold boot → BT OFF, Wi-Fi ON PASS PASS
Cold boot → BT OFF, Wi-Fi OFF PASS PASS

Key Takeaways

  1. Bluetooth's pre-reboot state is the decisive trigger. Whether Wi-Fi is ON or OFF before reboot does not prevent the failure if internal Bluetooth was active.
  2. A second warm reboot from the broken state recovers. Since neither btusb nor rtw88_8723de successfully initializes during the failed boot, the chip remains unconfigured. The subsequent warm reboot then allows the hardware to reset cleanly.

4. Kernel Source Root-Cause Analysis

4.1 Missing Shutdown Handler in drivers/bluetooth/btusb.c

In drivers/bluetooth/btrtl.c, Realtek defines btrtl_shutdown_realtek(struct hci_dev *hdev), which sends HCI_OP_RESET. 

/*
 * According to the vendor driver, BT must be reset on close to avoid
 * firmware crash.
 */

However, btusb_driver registers .disconnect = btusb_disconnect but does not register a .shutdown callback.

During kernel_restart(), the kernel executes device_shutdown(). The USB driver's disconnect callback is not a substitute for a shutdown callback.

The observed shutdown path leaves the Realtek Bluetooth firmware resident in chip RAM without an explicit HCI reset through the driver's shutdown sequence.

4.2 Incomplete Shutdown Sequence in drivers/net/wireless/realtek/rtw88/pci.c

rtw_pci_shutdown() invokes chip->ops->shutdown(rtwdev), which reaches rtw8723d_shutdown().

The latter only sets BIT_USB_SUS_DIS in REG_HCI_OPT_CTRL.

The existing shutdown sequence then transitions the PCI device to PCI_D3hot without first executing the complete driver power-off sequence or explicitly disabling PCI interrupts while RTW_FLAG_POWERON is still active.

4.3 Critical Deadlocks and Edge Cases Discovered During Testing

1. Do Not Call btusb_disconnect() or usb_reset_device() Inside usb_driver.shutdown()

Deadlock risk:

During device_shutdown(), the device lock is already held. Calling hci_unregister_dev() through btusb_disconnect(), or invoking usb_reset_device(), from the USB shutdown callback can deadlock on the USB device mutex.

Testing demonstrated that this approach can trigger a kernel panic during reboot.

2. Do Not Wake an Autosuspended Controller That Was Never Opened

Unconditionally calling usb_autopm_get_interface() inside btusb_shutdown() can wake an autosuspended Bluetooth controller even when Bluetooth was disabled in userspace throughout the session.

In that situation, __hci_cmd_sync() may abort with -ENETDOWN because HCI_UP is not set. This caused consecutive warm reboots with Bluetooth OFF to become unreliable during testing.

Solution: Track whether Bluetooth was actually opened during the current session using BTUSB_NEEDS_SHUTDOWN_RESET.

Set this flag in btusb_open(). During shutdown, wake and reset the controller only if the flag was set. Always clear needs_remote_wakeup and stop active URBs.

7. Installation & Rollback

Prerequisites

Refer to REQUIREMENTS.txt for the required kernel headers and build tools.

  • base-devel
  • linux-headers or matching linux-omarchy-headers

Installation

chmod +x install.sh
./install.sh
Important: First Boot After Installation

After installation completes, perform one full shutdown. Power the laptop off completely, then turn it back on. This ensures the patched modules are loaded cleanly.

Verify Active Module Overrides

modinfo btusb rtw88_pci | grep -E "filename|srcversion"

Both modules should resolve to: 

/lib/modules/$(uname -r)/updates/

Rollback to Stock Kernel Modules

./install.sh --uninstall

This removes the installed overrides and restores the stock kernel modules after the appropriate module refresh and reboot.
